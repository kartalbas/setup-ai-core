What runs now, printed the same way every time: the board counts and every agent process on this
machine (claude, codex, agy, gemini), each with its session name, pid, model, effort, minutes
running, the issue references in its command line, and whether it is a session, a run or a
resumed run. The runs an agent started stand indented under it. Under the table, REACH names the
command that reaches each agent, as its CLI reports it: claude attach <id> for a background
session, claude --resume <session id> for an interactive one, codex resume <id> where the
system shows the codex session file a process holds open, and a dash where nothing reports one.
Who works on what and what comes next is not measured; the coordinator says it, from what it
knows. Where no agent runs, and with
--tokens, it prints the usage windows, the pace, what an issue costs, the tokens and the context
of the day, the open work, and what is ready to close or open on the last column. No model is
involved: status.sh reads the board and the process list, and lib/status.mjs counts.

The usage line is the windows of the tool whose shell runs status (Codex, agy or Claude, the order of
`ai-core usage`), read by the reader `ai-core usage` uses (lib/usage.sh), and shown as the share used, as
`ai-core usage` shows them. Codex's and agy's are named for the tool, with the time the tool recorded them;
agy shows every group of models. A tool with no reader, and a reading that fails, are named on that line,
never replaced by Claude's windows. The pace is a board figure: the issues closed on the board in the last 24
hours, the same whatever the tool. What an issue costs of a window, the tokens and the context come from
Claude Code's own records, so in the shell of another tool those three lines say "no source for <tool>", never
Claude's figures and never a zero. The tokens count the sessions that started in the project folder or beneath
it, its clones and their worktrees, and no other folder whose name only begins like it.

The reviews line counts the review verdicts of the last 14 days (the days of the pace) per builder setup, model
and effort: how many GO, how many NO, and how many GO carried REPAIRED lines. It reads every comment page of each
board card whose title starts with "Plan: packages", open or closed, and counts a comment whose first line is
`REVIEW <area>: GO` or `REVIEW <area>: NO` and whose second line is `Reviewer: <name> (<model>, <effort>). Builder:
<name> (<model>, <effort>).` A verdict with no such line is counted as unattributed. A NO that only asks for a full
review, an exact repost and two verdicts that contradict each other for the same reviewer and builder sessions are
named and not counted. Comments in the RE-CHECK, PLAN CHECK or VERDICT: shapes, and plan issues whose comments could
not be read, are shown as unmeasured with their count; a tally with an unreadable plan issue says it is incomplete.

With TRACKER=forgejo, `ai-core status [OWNER/REPO...] --tokens` prints this page over the issues the status/
labels name, open and closed; Forgejo has no board, so the page names it OWNER/forgejo, it has no epics, and it
has no tally of reviews. Without --tokens the page of a Forgejo tracker ends with the TESTING block of the
open issues in testing it lists, the landing and the proof read from each issue's timeline as issue-close
reads them; an issue whose timeline could not be read is that issue's ❓ line.

Without --tokens or --issues the page ends with two blocks git answers at that moment. TESTING
lists every card in testing with where its work is live: the newest commit on the default branch
that names the issue (a commit names an issue by its number from the issue's creation on), and per environment of LIVE_TAGS in the .ai-core/config.env of the clone of its repository where that names one, else the project folder's list, whichever checkout this runs in
(status-sync reads the first environment of the same list), the first release tag by date that contains it, or the commit's landing where the environment is `landed`. A tag's date is an annotated tag's own, and a lightweight tag's
commit's. The newest commit is the one whose message names the issue anywhere in its text, the
issue's own full reference and a bare #N alike, never another repository's or a longer number. The
first environment is the last stage, the one whose release makes a card's proof due. A card its release
carries is 🔴 "proof due on <environment> since <age>" with that release until the tracker holds a proof
that status-sync (GitHub) or issue-proof (Forgejo) would count, a trusted "Proven on <environment>:" comment
after the landing record; with that proof it is 🟢 "proven on <environment>", and it closes with the next
status-sync or issue-proof. A card no release of that environment carries yet is ⏸ "waits for the release of
<environment>" with its tag pattern. A card live on a later environment only is due for its proof there, 🟡,
and 🔴 once that environment has carried it longer than PROOF_HOURS of the project folder's .ai-core/config.env.
Where LIVE_TAGS is empty, every release tag of the card's repository is its release, as status-sync reads
it: the card is 🔴 from the first tag that contains the landing, and ⏸ "waits for a release of <repository>
(every tag)" while none does.
An environment whose value is `command` is delivered by what LIVE_RELEASE_COMMAND of the clone the
work landed in answers (lib/live-release.sh): its newest completed delivery, shown with its source
and time. Such a card is read by the landing record its issue holds, the newest one of a trusted
author after the last reopening within the last 50 comments, and by the whole list of that clone,
not the project folder's. Status asks the tracker for the landing and the proof of every card in testing, once each: on
GitHub the comment pages and one request for the last reopening, which is the time it adds. A card whose landing, delivery or fetch could not be read is
`unknown`, with its full repository and the reason: it is counted as unknown, never read from the
commits instead, and the command exits 1 after the page. The live counts are per environment, by
its exact name and by whether it is the first of its list or a later one. TREES lists the issue worktrees `finish-issue --sweep --dry-run` keeps whose
last commit or uncommitted change is older than a day, with the sweep's reason; it and the agent table
name a worktree by the issue number of its checked-out branch, else of its directory. The clone of each
repository with a card in testing, the folder whose origin is that repository, is fetched once per
call, for at most a minute.
